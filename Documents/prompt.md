> и `tz-2-realizaciya.md` (§ 8–§ 13: архитектура, метрики, критерии приёмки, риски).
> Нумерация разделов и идентификаторы требований сквозные для обоих файлов.

## РОЛЬ
Ты — senior full-stack инженер по десктоп-приложениям. Твоя задача — спроектировать и реализовать локальное Windows-приложение «Текст по-человечески» согласно приложенному ТЗ (`tz-1-trebovaniya.md` + `tz-2-realizaciya.md`). ТЗ — единственный источник истины: при любом сомнении сверяйся с номером FR/критерия (A1–A16, B1–B18, §11.3 во второй части).

## ЦЕЛЬ
Инструмент, который переписывает научный/профессиональный текст (русский язык) «прозой вместо списков», без клише и **физически не меняя** числа, имена, термины и ссылки. Ключевое отличие от ChatGPT — гарантия неизменяемого + отчёт проверки смысла.

## ЖЁСТКИЕ ИНВАРИАНТЫ (нарушение = брак, см. §11.3)
1. **Гарантия неизменяемого через пайплайн, а не через промпт.** Защищённый фрагмент (число, имя, аббревиатура, латиница, URL, номер источника) изымается из отрывка → заменяется токеном-заглушкой (например `⟦P1⟧`) → после генерации возвращается дословно. Модель никогда не видит защищённый текст как редактируемый.
2. Порядок абзацев и разделов не меняется **ни на одном** уровне ползунка (FR-2.2).
3. Новая фактическая информация не добавляется **никогда** (FR-2.1).
4. Направление/сила утверждения («не повышает», «некоторые») сохраняются (FR-7.3).
5. Экспорт с 🔴-абзацами — только после явного подтверждения автора (FR-7.5).
6. Первый облачный запуск всегда показывает модалку M1 (FR-SEC-2).

## СТЕК (зафиксирован ТЗ, §8.2)
- Оболочка: **Tauri** (Rust core) — из-за лимита RAM ≤ 2 ГБ и веса дистрибутива.
- Фронт: **React + TypeScript**.
- Редактор: движок с inline-диапазонами (ProseMirror/Deco–Mark) — нужен для подсветки правок и маркеров защиты.
- Логика обработки: отдельный service-процесс (очередь, батчинг, retry, стриминг).
- Хранение: **SQLite** в каталоге данных + файл DOCX-оригинала (неизменяемый эталон).
- Ключи API: защищённое хранилище Windows (DPAPI / Credential Manager), маска в UI.
- Локальный движок: GGUF 3–4B через llama.cpp/Ollama. Облако: OpenAI-совместимый API.
- DOCX round-trip: правятся только текстовые runs внутри существующей структуры; форматирование, сноски, колонтитулы, таблицы — не трогаем (FR-9.2, B2/B3).

## ДВА ДВИЖКА — ЕДИНЫЙ ИНТЕРФЕЙС
Абстракция `Engine` с двумя реализациями (cloud/local). Переключение не меняет функций/экранов/пресетов, только скорость, качество и предупреждение о передаче данных (FR-8.3.1). Локальный пакет — фоновый, прерываемый, возобновляемый (S19).

## ЧТО СТРОИМ ПРЯМО СЕЙЧАС — ЭТАП «ЗАВТРА» (A1–A16)
Сквозной демонстрационный контур на реальном фрагменте диплома. Объём:
- **E1/E3/E4 полностью**: лента сверху + панель слева + документ по центру; светлый академичный стиль; шрифт ≥16px, интерлиньяж ≥1.5.
- 4 пресета F1–F4 + ползунок интенсивности 1–5 (реально влияют на генерацию, A4/A5).
- Импорт из буфера (E2, буфер), распознавание абзацев, счётчик знаков/страниц (1800 зн./стр.).
- Автозащита чисел и имён (A6, R1/R2=100%) + ручная защита «выделение → Не трогать» (A7).
- Сравнение «было/стало» рядом, синхронная прокрутка, приёмка по абзацам, «Принять всё/Отклонить всё», Ctrl+Z (A8/A9).
- Упрощённый отчёт проверки смысла E5 (таблица по абзацам 🟢/🟡/🔴 + сводка, A10).
- Анти-шаблон: словарь клише ≥150, запрет клише и новых списков в результате (A11).
- Точечный режим: выделение → 2–3 варианта с пометкой отличия → принять, ≤10 с (A12).
- Модалка M1 перед первым облачным запуском (A13).
- Экспорт чистого текста (не DOCX) + сохранение проекта с версией (A14).
- Пустые/ошибочные состояния как полноценные экраны: S1, S12, S15, S16 (A16).
- **Осознанно НЕ делаем на этом этапе:** DOCX round-trip, локальный движок, профиль стиля, журнал аудита, недельный лимит, ГОСТ — только заглушки/пустые состояния.

## АРХИТЕКТУРА ПРАВОК (модель данных, §6.1)
Проект → Абзацы (original text, current text, варианты 2–3, статус `original|pending|processed|accepted|rejected|warning|error`, защищённые фрагменты со смещёнными позициями, результат проверки смысла). Отдельно StyleProfile (не удаляется с проектом), словари защиты, ключи.

## КОНВЕЙЕР ОБРАБОТКИ АБЗАЦА (реализуй именно так)
1. Токенизация: выделить и вынести защищённые фрагменты → заглушки.
2. Системный промпт движку: пресет F1–F4 + уровень 1–5 + анти-шаблон + «не менять заглушки, не добавлять фактов, сохранить регистр».
3. Генерация (стриминг для точечного режима).
4. Возврат заглушек дословно.
5. Валидация: R1/R2/R3 (числа/имена/ссылки дословно), R4 (полнота фактов), R6 (нет новых фактов), H2 (клише), H1 (нет новых списков), H5 (регистр).
6. При провале — авторетрай до 2 попыток, иначе статус 🟡/🔴 (FR-4.3).

## ОГРАНИЧЕНИЯ ПРОИЗВОДИТЕЛЬНОСТИ (§8.4)
Точечный 1 абзац облако ≤10 с · пакет облако 5 стр ≤5 мин · импорт DOCX 100 стр ≤30 с · отклик UI ≤100 мс · RAM ≤2 ГБ · автосохранение ≤30 с.

## ФОРМАТ РАБОТЫ
1. Сначала верни краткий технический план: структура проекта Tauri, модули фронта, схема SQLite, контракт `Engine`, конвейер обработки — и дождись подтверждения.
2. Затем реализуй этап «Завтра» (A1–A16) рабочим кодом, по экранам, с реальными (не mock) состояниями.
3. После каждого логического блока показывай diff и как проверить соответствие критерию (номер A/B/FR).
4. Не выдумывай требования сверх ТЗ; функции §5.12 (этап 2) не реализуй.

## ПРИЁМКА
Пройти чек-лист §11.1 (завтра) и §11.2 (MVP). Особый контроль §11.3 — дефекты-блокировщики: любая изменённая цифра, потерянное имя, новый факт, смена силы утверждения, сломанный DOCX, потеря правок, облако без M1, разговорный регистр в F1/F2 — это отклонение.

### Приложение: тестовый вход для демонстрации
Взять 1 реальный фрагмент ВКР (15–20 абзацев, спортивная тематика, содержит числа, %, ±, имена, ссылки `[12]` и `(Иванов, 2019)`, хотя бы один маркированный список и клише «важно отметить»). Прогнать F1 vs F3 и уровень 1 vs 5; провести слепой тест (исходник / результат / ChatGPT), зафиксировать П1–П4 как ориентир.
